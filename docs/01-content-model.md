# NEURICA — Content Model v0.1
Специфікація об'єктів для neurica.net. Призначення: визначити, що саме
проектується, до того як починається дизайн сторінок.
Формула, яку ця схема має захищати:
> Neurica — жива лабораторія, але не другий production-контур.
Схема не описує намір — вона робить його перевірюваним на етапі збірки.
Правила в розділі 5 виконуються білдом; порушення зупиняє збірку або
понижує статус автоматично. Дисципліна не потрібна.
---
## 1. Дві осі
Тип і статус — різні речі й не можуть жити в одному полі.
| Вісь | Питання | Змінюється |
|---|---|---|
| `type` | що це за робота за родом | ні |
| `status` | у якому вона стані зараз | так |
Приклад, який без двох осей не виражається: демо відключили, сторінка
лишилася як опис реальної роботи. Це `CASE` + `FROZEN`. Однією віссю
доводиться або збрехати про тип, або втратити сторінку.
---
## 2. `type` — рід роботи
### `EXPERIMENT`
Є відкрите питання і невідомий наперед результат. Робота може закінчитися
висновком «не працює», і це повноцінний результат.
### `PROTOTYPE`
Результат відомий, невідома якість виконання. Будується, щоб перевірити
механіку, а не гіпотезу. Не призначений для тривалого використання.
### `TOOL`
Невеликий робочий інструмент, зроблений для того, щоб ним користувалися.
Відрізняється від прототипа життєвим циклом: прототип викидають, інструмент
підтримують.
### `CASE`
Реальна робота, виконана в іншому контурі. Документація задачі, архітектури
й результату. Може мати інтерактивну поверхню — але вона демонстраційна.
### `VISUAL_STUDY`
Візуальне дослідження без функціональної частини.
### `EDITORIAL`
Текстовий об'єкт: маніфест, позиція, розбір.
**Межа EXPERIMENT / PROTOTYPE.** Одне питання: чи можна наперед описати,
який результат вважатиметься успіхом? Якщо так — `PROTOTYPE`. Якщо
відповідь «залежить від того, що вийде» — `EXPERIMENT`. Без цього тесту
`EXPERIMENT` за кілька місяців з'їде назад у значення «щось недороблене»
і перестане нести інформацію.
---
## 3. `status` — стан
### `LIVE`
Працює по-справжньому. Є власник, є відповідальність за працездатність.
Користувач має право розраховувати, що воно відкриється.
### `DEMO`
Інтерактивне, але на зафіксованих або синтетичних даних. Гарантій немає,
і UI це показує.
### `STATIC`
Немає рантайму. Значення за замовчуванням для `VISUAL_STUDY`, `EDITORIAL`
і більшості `CASE`.
### `FROZEN`
Було інтерактивним, ендпоінт відключено. Сторінка лишається як запис.
### `ARCHIVE`
Втратило актуальність або замінене іншим об'єктом. Доступне за прямим
посиланням, зі стрічки прибране.
---
## 4. Поля
```
Item
  slug                required   унікальний, kebab-case
  title               required
  type                required   EXPERIMENT | PROTOTYPE | TOOL | CASE
                                 | VISUAL_STUDY | EDITORIAL
  status              required   LIVE | DEMO | STATIC | FROZEN | ARCHIVE
  art_direction       required   MONOCHROME | CHROMATIC | MATERIAL | ORGANIC
  summary             required   один рядок механіки:
                                 "inventory → catalog → PDF"
  cover               required
  year                required
  tags[]
  media[]
  body                           обов'язкове для CASE та EDITORIAL
  context                        ALTACO | EONYX | EXTERNAL | INTERNAL
  # рантайм
  endpoint                       обов'язкове для LIVE і DEMO
  owner                          обов'язкове для LIVE
  last_checked                   обов'язкове для LIVE, ISO date
  # походження збірки
  source_repo                    репозиторій, з якого зібрано поверхню
  build_ref                      коміт або тег, зафіксований у білді
  # дані
  data_mode           required   NONE | SYNTHETIC | SANITIZED | LIVE_BUSINESS
  data_snapshot_date             обов'язкове якщо data_mode ≠ NONE
                                 і не SYNTHETIC
  data_fields[]                  перелік полів, відданих у публічну збірку
```
### `data_mode`
- `NONE` — даних немає (візуальні студії, редакційні матеріали).
- `SYNTHETIC` — вигадані дані.
- `SANITIZED` — реальні дані, з яких прибрано операційні поля.
- `LIVE_BUSINESS` — прямий доступ до бізнес-даних. **Не допускається на
  Neurica** (див. 5.1). Значення існує лише для того, щоб його можна було
  явно відхилити.
### `data_fields[]`
Білий список. Поле є в публічній збірці тільки якщо воно перелічене тут.
Не чорний список: чорний доводиться доповнювати щоразу, коли в джерелі
з'являється нова колонка, і одного пропуску достатньо.
Для ALTACO публічними лишаються: назва, виробник, колекція, формат,
обробка, фото, `availability` як прапорець. Не потрапляють: глибина
запасу, резерви, внутрішні й закупівельні ціни, рух товару, історія,
будь-які службові поля.
### `build_ref`
Демо-поверхня — це артефакт, зібраний з чужого репозиторію на конкретному
коміті, а не з'єднання з працюючим сервісом. Різниця практична: артефакт
не може розійтися з джерелом і не падає разом із ним. Якщо в об'єкта є
`endpoint`, але немає `build_ref`, це означає з'єднання — див. 5.2.

## 4a. Локалізація
Сайт двомовний: `uk` (за замовчуванням, корінь) і `en` (`/en/`).
### Розділення полів
**Структурні — спільні, в одному екземплярі:**
```
slug  type  status  art_direction  cover  year  context
endpoint  owner  last_checked  source_repo  build_ref
data_mode  data_snapshot_date  data_fields[]
```
**Локалізовані — по одному на мову:**
```
title  summary  body  tags[]
```
Структурні поля не дублюються по мовах. Дубльовані — розходяться: об'єкт
стає `DEMO` в одній мові й `LIVE` в іншій, і правило 5.1 виконується
вибірково. Це та сама проблема розходження, через яку демо вбудовується
артефактом, а не підключається.
### Форма зберігання
```
src/content/work/<slug>/
  index.yaml     структурні поля
  uk.md          title, summary, body, tags
  en.md          title, summary, body, tags
```
### Що не перекладається ніколи
Значення `type`, `status`, `art_direction` — англійські в обох версіях.
Це технічний регістр, той самий, який у токенах відданий mono. «КЕЙС ·
ДЕМО» ламає і типографічне трактування, і сенс: це маркери стану, а не
текст для читання.
`summary` перекладається як речення, але формульна форма зберігається в
обох мовах: `inventory → catalog → PDF` лишається як є.
`slug` спільний для обох мов. URL відрізняються лише префіксом:
`/work/altaco-catalog` і `/en/work/altaco-catalog`.

## 5. Правила збірки
### 5.1 Бізнес-дані ніколи не бувають LIVE
```
if data_mode == LIVE_BUSINESS: fail build
if context == ALTACO and status == LIVE: fail build
```
Це головне правило файлу. Воно і є технічним записом формули «не другий
production-контур». Стеля для всього, що торкається комерційних даних, —
`DEMO`.
### 5.2 Демо вбудовується, а не підключається
```
if status in (LIVE, DEMO) and endpoint and not build_ref: fail build
```
### 5.3 LIVE понижується сам
```
if status == LIVE and (now - last_checked) > 45 days:
    status = FROZEN
    log warning
```
Не видалення. Відключене демо часто лишається добрим кейсом — вимикається
рантайм, сторінка живе далі.
### 5.4 Обов'язковість за станом
```
if status == LIVE and not owner: fail build
if status == DEMO and data_mode == NONE and endpoint: fail build
if status == DEMO and data_mode != SYNTHETIC and not data_snapshot_date:
    fail build
```
### 5.5 Статус показується тільки коли щось означає
`STATIC` не рендериться. `VISUAL_STUDY · STATIC` — шум: у візуальної
студії й так нема чому працювати.
Рендериться: `LIVE`, `DEMO`, `FROZEN`, `ARCHIVE`.
```
CASE · DEMO           дані від 12.08.2026
EXPERIMENT · LIVE
PROTOTYPE · FROZEN
VISUAL STUDY
```
Для `DEMO` дата снепшоту показується поруч зі статусом. Видима дата
знімає питання про свіжість, не вимагаючи жодних гарантій.
### 5.6 Чергування арт-дирекшенів
```
if 3 adjacent cards share art_direction: warn
```
Правило верстки стрічки, а не заборона. Чотири візуальні території мають
чергуватися, інакше сторінка читається як один напрямок, а система — як
його відсутність.
### 5.7 Обидва переклади обов'язкові
```
if not exists(uk.md) or not exists(en.md): fail build
```
Перемикач мови є на кожній сторінці. Якщо об'єкт існує лише в одній
мові, перемикання веде в 404 — і робить це на випадковому підмножині
сторінок, тобто помітно не одразу.
При п'яти об'єктах вимога обох перекладів дешевша за будь-який механізм
запасного варіанту. Якщо колись об'єктів стане достатньо, щоб це
заважало, вводиться поле `translations[]` із явним переліком доступних
мов — але не раніше.

## 6. Стартовий набір
П'ять слагів: `altaco-catalog`, `agent-workflow`,
`synthetic-structures-01`, `organic-intelligence`, `what-neurica-is`.
Приклад повного об'єкта — `altaco-catalog`:
```yaml
# work/altaco-catalog/index.yaml
type: CASE
status: DEMO
art_direction: MATERIAL
year: 2026
cover: ./cover.jpg
context: ALTACO
data_mode: SANITIZED
data_snapshot_date: 2026-08-12
source_repo: altaco-platform
build_ref: <tag>
```
```yaml
# work/altaco-catalog/uk.md
title: Динамічний каталог ALTACO
summary: inventory → catalog → select → PDF
```
```yaml
# work/altaco-catalog/en.md
title: ALTACO Dynamic Catalog
summary: inventory → catalog → select → PDF
```
Решта:
| slug | type | status | art_direction | context |
|---|---|---|---|---|
| `agent-workflow` | PROTOTYPE | STATIC | MONOCHROME | EONYX |
| `synthetic-structures-01` | VISUAL_STUDY | STATIC | CHROMATIC | — |
| `organic-intelligence` | VISUAL_STUDY | STATIC | ORGANIC | — |
| `what-neurica-is` | EDITORIAL | STATIC | MONOCHROME | EONYX |
П'ять об'єктів, чотири арт-дирекшени, одна інтерактивна поверхня, десять
файлів прози. Шостий об'єкт додається, коли з'явиться справжній, а не для
заповнення сітки.
---
## 7. Що ця схема свідомо не робить
Не описує сторінки, навігацію й компоненти. Content model визначає, які
об'єкти існують; інформаційна архітектура (крок 03) визначає, як їх
показувати. Якщо тут з'являються поля на кшталт `hero_position` —
структура почала диктуватися дизайном, тобто в зворотний бік.
