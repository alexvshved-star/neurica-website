# Архітектура

## Стек

- **Astro 7** (`astro build`), TypeScript `strict: true`.
- **Astro content collections** з кастомним loader'ом
  (`src/content.config.ts`) — не стандартний glob-loader, бо кожен
  об'єкт складається з трьох файлів (`index.yaml` + `uk.md` + `en.md`),
  а потрібна одна крос-файлова Zod-валідація на об'єкт.
- **`@astrojs/sitemap`** — генерує `sitemap-index.xml`/`sitemap-0.xml`
  автоматично з усіх статичних маршрутів, врахувавши i18n-конфіг.
- **Без Tailwind** — токенна дизайн-система (`tokens.css`) вже є шаром
  утиліт; Tailwind дублював би його (рішення 006).
- **Без UI-фреймворків, без клієнтського рантайму.** Сторінки — чистий
  Astro (`.astro` файли рендеряться в статичний HTML на збірці, нуль
  JS у браузері за замовчуванням).
- `js-yaml` — єдина build-time залежність поза Astro/TypeScript,
  потрібна кастомному loader'у для парсингу `index.yaml` і
  frontmatter у `.md`.

### Чому `src/content.config.ts`, а не `src/content/config.ts`

Astro 7 (стабільний на момент цієї сесії) видалив підтримку
"legacy"-розташування `src/content/config.ts` — файл конфігурації
колекцій має лежати в корені `src/`, поруч із директорією `content/`,
не всередині неї. Це відрізняється від дерева каталогів, накресленого
в брифі сесії; решта структури (`src/content/work/<slug>/...`)
лишилася без змін.

## Збірка

`npm run build` = `astro build`:

1. Content Layer сканує `src/content/work/*/`, для кожного slug читає
   `index.yaml` + `uk.md` + `en.md`, зводить в один об'єкт і прогонює
   крізь `workSchema` (structural + localized + `.superRefine()` з
   правилами розділу 5 моделі). Порушення — `fail build` з
   повідомленням, що називає slug і номер правила.
2. Astro генерує статичні маршрути для всіх сторінок у `src/pages/`
   (включно з динамічними `work/[slug].astro`, по одному на кожен
   валідний об'єкт колекції) — у `uk` (корінь) і `en` (`/en/`).
3. `@astrojs/sitemap` збирає всі згенеровані маршрути в
   `dist/sitemap-index.xml`.

Результат — статичні HTML-файли в `dist/`, без сервера, без рантайму.

## Деплой — Netlify

`netlify.toml`: `command = "npm run build"`, `publish = "dist"`.
Попередня версія сайту публікувала корінь репозиторію напряму
(`publish = "."`, чистий HTML без збірки) — після переходу на Astro
це мало б віддавати вихідники, тому `publish` тепер вказує на build
output.

Security- і cache-headers перенесені без змін із попереднього
`netlify.toml` (коміт `fdcd322`). Редіректи оновлені під нову мовну
схему (`/index-en`, `/en` → `/en/`, 301) — рішення 005.

## Чому без бекенду

Формула розділу `00-what-neurica-is.md`: Neurica — жива лабораторія,
не другий production-контур. Бекенд, БД, авторизація означають SLA,
чергування, відповідальність за uptime — саме те, від чого ця
поверхня свідомо відмовляється. Усе, що починає цього потребувати,
переїжджає у свій контур (наприклад ALTACO), а на Neurica лишається
як `CASE`/`DEMO` — вбудований артефакт, а не з'єднання (правило 5.2).

Форми, аналітика, авторизація — поза межами цього каркасу (NON-GOALS
сесії relaunch/scaffold). Стара форма підписки на бету існувала на
боці Netlify Forms у попередній версії сайту; рішення, чи повертати
контактну точку на Neurica, відкладено (рішення 011).
