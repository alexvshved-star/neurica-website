# Архітектура

## Поточний стек

Це опис реалізованого каркасу. Цільова архітектура пілота й план
переходу — [08-altaco-pilot.md](./08-altaco-pilot.md).

- **Astro 7** (`astro build`), TypeScript `strict: true`.
- **Astro content collections** з кастомним loader'ом
  (`src/content.config.ts`) — не стандартний glob-loader, бо кожен
  об'єкт складається з трьох файлів (`index.yaml` + `uk.md` + `en.md`),
  а потрібна одна крос-файлова Zod-валідація на об'єкт.
- **`@astrojs/sitemap`** — генерує `sitemap-index.xml`/`sitemap-0.xml`
  автоматично з усіх статичних маршрутів, врахувавши i18n-конфіг.
- **Без Tailwind** — токенна дизайн-система (`tokens.css`) вже є шаром
  утиліт; Tailwind дублював би його (рішення 006).
- **Без UI-фреймворків, без клієнтського рантайму за замовчуванням.**
  Сторінки — чистий Astro (`.astro` файли рендеряться в статичний HTML
  на збірці, нуль JS у браузері). Виняток — каталог ALTACO: та сама
  статична збірка, але з власним браузерним JS (фільтри, кошик,
  генерація PDF) — розділ «Рантайм робочого пілота» нижче.
- `js-yaml` — єдина build-time залежність поза Astro/TypeScript,
  потрібна кастомному loader'у для парсингу `index.yaml` і
  frontmatter у `.md`.

### Чому `src/content.config.ts`, а не `src/content/config.ts`

Astro 7 (стабільний на момент цієї сесії) видалив підтримку
"legacy"-розташування `src/content/config.ts` — файл конфігурації
колекцій має лежати в корені `src/`, поруч із директорією `content/`,
не всередині неї. Це відрізняється від дерева каталогів, накресленого
в брифі сесії; решта структури (`src/content/work/<slug>/...`)
лишилася без змін.

## Збірка

`npm run build` = `astro build`:

1. Content Layer сканує `src/content/work/*/`, для кожного slug читає
   `index.yaml` + `uk.md` + `en.md`, зводить в один об'єкт і прогонює
   крізь `workSchema` (structural + localized + `.superRefine()` з
   правилами розділу 5 моделі). Порушення — `fail build` з
   повідомленням, що називає slug і номер правила.
2. Astro генерує статичні маршрути для всіх сторінок у `src/pages/`
   (включно з динамічними `work/[slug].astro`, по одному на кожен
   валідний об'єкт колекції) — у `uk` (корінь) і `en` (`/en/`).
3. `@astrojs/sitemap` збирає всі згенеровані маршрути в
   `dist/sitemap-index.xml`.

Результат — статичні HTML-файли в `dist/`, без сервера, без рантайму.

## Деплой — Netlify

`netlify.toml`: `command = "npm run build"`, `publish = "dist"`.
Попередня версія сайту публікувала корінь репозиторію напряму
(`publish = "."`, чистий HTML без збірки) — після переходу на Astro
це мало б віддавати вихідники, тому `publish` тепер вказує на build
output.

Security- і cache-headers перенесені без змін із попереднього
`netlify.toml` (коміт `fdcd322`). Редіректи оновлені під нову мовну
схему (`/index-en`, `/en` → `/en/`, 301) — рішення 005.

## Рантайм робочого пілота

Каталог ALTACO залишається статично згенерованим (той самий Astro
build, що й решта сайту), але його сторінки самі містять браузерний
JS — це виняток із «нуль JS у браузері за замовчуванням» вище, і саме
тут, а не в окремому бекенді, живе логіка пілота:

- **Фільтри й пошук** (`Catalog.astro`) — клієнтський JS, без
  серверних запитів; шість полів, URL зберігає стан.
- **Кошик** (`src/catalog/cart.mjs`) — `localStorage`
  (`altaco-cart-v1`), лише ID і кількості; ціни й характеристики
  завжди беруться з поточного знімка, не з кошика.
- **Генерація КП і прайсів** — клієнтський jsPDF
  (`src/catalog/{offer,pricelist,pdf-file,pdf-actions}.{mjs,ts}`),
  модуль і ресурси довантажуються лише на запит; перегляд/завантаження/
  Web Share — теж у браузері, без серверного збереження.

Власного бекенду, авторизації команди й автоматичної синхронізації
з Google Sheets немає: імпорт — контрольований, ручний знімок
(`scripts/catalog/import-stock.mjs`), не жива інтеграція. Приватні
дані (закупівельні ціни, точні залишки, службові поля) не вбудовуються
в публічний HTML/JS/JSON — білий список полів перевіряється
`validateSnapshot()` (`src/catalog/model.mjs`). Якщо колись знадобляться
захищені операції чи серверна логіка — конкретний спосіб авторизації
й виконання ще не обраний. Деталі контракту, імпорту й перевірок —
[09-altaco-catalog.md](./09-altaco-catalog.md); вимоги до перенесення
в ALTACO Platform — [08-altaco-pilot.md](./08-altaco-pilot.md).

## Заявки на тестування — 16.09.2026

У «Контактах» (`/about/`, `/en/about/`) розміщено `PilotForm.astro`.
Це статична HTML-форма Netlify Forms, native POST без клієнтського
зберігання персональних даних. Окремі імена `neurica-pilot-uk` та
`neurica-pilot-en` відділяють нові заявки від історичної форми `beta`.
Обов’язкові: ім’я, email, напрям і задача; компанія/роль та телефон
необов’язкові. Є honeypot, мовне поле й локалізовані сторінки подяки.
Валідація браузера перевіряє required/email, а приймання виконує Netlify.
Потрібне увімкнене form detection; листи-сповіщення залежать від
налаштувань Netlify і не налаштовуються цим кодом. Заявки не є
автоматичною видачею доступу до прототипів. Контроль реального отримання
заявки в панелі Netlify — окрема перевірка, не результат локальної збірки.
Документація сервісу: https://docs.netlify.com/manage/forms/setup/
