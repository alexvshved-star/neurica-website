# Специфікація для автора контенту

Цей документ — усе, що потрібно, щоб підготувати й здати контент для
об'єкта `work`, не заглядаючи в код. Джерело істини для полів і правил
збірки — [`01-content-model.md`](./01-content-model.md); цей документ
додає практичні числа (розміри, символи), яких там немає.

---

## 1. Файли одного об'єкта

```
src/content/work/<slug>/
  index.yaml            структурні поля (спільні для uk/en)
  uk.md                 title, summary, tags[], body, media (alt/caption)
  en.md                 те саме англійською
  cover.<ext>            обкладинка
  01.<ext>, 02.<ext>…    media[] для VISUAL_STUDY, якщо є
```

`<slug>` — kebab-case, унікальний, стає частиною URL
(`/work/<slug>` і `/en/work/<slug>`) і не перекладається.

**Заглушки.** Поки файл зображення — тимчасова заглушка, а не фінальне
фото, називайте його з `.placeholder.` у назві:
`cover.placeholder.jpg`, `01.placeholder.jpg`. Збірка виводить
warning для кожного файлу з таким іменем — це навмисно, щоб заглушка
не проскочила в публікацію тихо. Коли зображення фінальне, приберіть
`.placeholder.` з назви й оновіть шлях у `index.yaml`.

---

## 2. Обов'язкові поля за `type`

Повний перелік полів — розділ 4 моделі контенту. Тут — тільки те, що
специфічно для типу.

| `type` | `body` | `media[]` | Примітка |
|---|---|---|---|
| `CASE` | **обов'язкове** | — | структура — розділ 4 нижче |
| `EDITORIAL` | **обов'язкове** | — | `cover` є, але не показується в тілі (лише картка/og:image) |
| `EXPERIMENT` | опційне | — | структура — розділ 4 нижче |
| `PROTOTYPE`, `TOOL` | опційне | — | акцент на самому об'єкті (`endpoint`), не на прозі |
| `VISUAL_STUDY` | опційне, коротке | типово так | проза тут заважає — розділ 3.4 IA |

Незалежно від типу: `title`, `summary`, `cover`, `published`,
`art_direction`, `data_mode` — завжди обов'язкові (розділ 4 моделі).

## 3. Зображення

### 3.1 Формат і пайплайн

JPEG або PNG на вхід (`astro:assets` сам генерує AVIF і WebP з
фолбеком на збірці — окремо готувати ці формати не потрібно).
Кладіть файл поруч із `index.yaml`, не в `public/`.

### 3.2 Розміри за `art_direction`

`--image-ratio` (`tokens.css`) відрізняється за напрямком — кожен
кроп має лишити **щонайменше 2400px по довшій стороні** після кропу.
Мінімальний розмір вихідника (уже кадрованого під свою пропорцію):

| `art_direction` | пропорція | мінімум (ш×в) |
|---|---|---|
| `MONOCHROME` | 4:3 | 2400 × 1800 |
| `CHROMATIC` | 16:9 | 2400 × 1350 |
| `MATERIAL` | 1:1 | 2400 × 2400 |
| `ORGANIC` | 3:4 (портрет) | 1800 × 2400 |

Якщо вихідник знятий не рівно в цій пропорції — кадруйте перед
експортом так, щоб після кропу довша сторона все одно лишалась
≥2400px; не покладайтесь на те, що збірка докадрує щось менше.

Збірка перевіряє фактичну пропорцію обкладинки проти цієї таблиці:
якщо відхилення понад 15% — `[image-ratio]` warning із slug і
фактичними розмірами. Не помилка (кроп однаково відбудеться), але
означає, що сюжет може постраждати від автоматичного кропу — варто
самостійно перевірити прев'ю.

### 3.3 `media[]` для `VISUAL_STUDY`

Структурне (`index.yaml`) і локалізоване (`uk.md`/`en.md`) розділені
так само, як решта полів моделі:

```yaml
# index.yaml
media:
  - id: m1
    src: ./01.jpg
  - id: m2
    src: ./02.jpg
```

```yaml
# uk.md / en.md (frontmatter)
media:
  m1: { alt: "Опис зображення 1", caption: "Опційний підпис" }
  m2: { alt: "Опис зображення 2" }
```

`alt` **обов'язковий** для кожного `id`, `caption` опційний. Кожен
`id` зі структурного файлу має мати відповідник в **обох** мовних
файлах — інакше збірка падає (`[media]`, той самий принцип, що 5.7
для перекладів). Типовий обсяг послідовності — 6–8 зображень; менше
теж технічно валідно, просто дослідження виглядає тонким.

### 3.4 og:image

Не готувати окремий файл. Збірка сама кропує `cover` по центру під
1200×630 (~1.91:1, стандарт Open Graph) для кожного об'єкта.

## 4. Довжина заголовка й summary — українською

`--type-display` (hero, `tokens.css`) доходить до `11rem` на desktop
і до `5rem` на mobile; український текст на 10–15% довший за
англійський при тому самому сенсі. Розрахунок нижче — інженерна
оцінка (Montserrat Black, середня ширина гліфа ≈0.62 від кегля,
`tracking-display: -0.03em`), не заміряна вручну; уточнити на кроці
05 за реальним рендером.

| Breakpoint | Опорний viewport | Кегль | Символів/рядок | Практичний ліміт (≈2 рядки) |
|---|---|---|---|---|
| Mobile | 390px | ≈62px | ≈9 | ≈18 символів |
| Desktop | 1680px (`--width-max`) | 176px (стеля) | ≈15 | ≈30 символів |

**Правило.** Заголовок до ~30 символів українською — безпечний на
обох breakpoint'ах у межах 2 рядків. Довше — не помилка (перенос
можлива свідома дія), але збірка виводить `[title-length]` warning
понад 30 символів, щоб це було видно до публікації, а не після.

`summary` не проходить через display-кегль, але за задумом моделі —
"один рядок механіки" (`inventory → catalog → PDF`). Орієнтир: до
~70 символів українською, щоб реально читалось як один рядок на
`--width-reading` (680px) при звичайному тексті. Довше — не помилка,
просто перестає бути "одним рядком".

## 5. Структура `body`

### `CASE`

Задача → підхід → результат. Три змістовні частини, необов'язково
формальні підзаголовки:
1. Що за задача і в якому контурі вона реально виконана
   (`context`/`source_repo` це вже кажуть структурно — тут людською
   мовою).
2. Як підійшли — ключове рішення, не повний technical writeup.
3. Що вийшло — конкретний результат, не загальні слова.

Якщо `status: DEMO` і є `endpoint` — блок демонстрації рендериться
окремо, над прозою (`RuntimeNotice`, автоматично). У `body` не треба
повторювати застереження про демо-дані — воно вже там.

### `EXPERIMENT`

Питання → що робили → що вийшло, **включно з "не спрацювало"**.
Негативний результат — повноцінний результат для цього типу (розділ
2 моделі контенту): не приховувати й не заминати, якщо гіпотеза не
підтвердилась.

### `VISUAL_STUDY`, `PROTOTYPE`/`TOOL`, `EDITORIAL`

Вільна форма. Для `EDITORIAL` — це вся сторінка (маніфест, позиція,
розбір), без обмежень структури.

## 6. Що ніколи не перекладається

- Значення `type`, `status`, `art_direction` — завжди англійські в
  обох мовних версіях (технічний регістр, mono-трактування).
- Формульна форма `summary` (`inventory → catalog → PDF`) —
  лишається як є в обох мовах, навіть коли решта речення перекладена.
- `slug` — спільний, різниця тільки в префіксі `/en/`.

Усе інше (`title`, `summary`-речення, `body`, `tags[]`, `alt`,
`caption`) — окремо для кожної мови, обидві обов'язкові (5.7).

---

## 7. `feature`

Одне ручне булеве поле в `index.yaml`. Максимум **3** об'єкти
одночасно — понад це збірка виводить `[feature]` warning (не fail).
Впливає на масштаб картки на головній (`large`, розділ 4
`06-information-architecture.md`) — решта масштабу виводиться з
`type`/`status` автоматично, вручну більше нічого не задається.

---

## 8. `endpoint` / `build_ref` — без плейсхолдерів

Правило 5.8 (`01-content-model.md`) забороняє: `example.com`,
`localhost`, `<...>`, `TODO`, `TBD`, і `build_ref`, що не схожий на
SHA чи тег. Якщо демо ще не існує — не заповнювати ці поля взагалі
(`status: STATIC`), а не ставити тимчасове значення. Саме так
трапився неробочий `altaco-catalog.endpoint` у попередній сесії —
5.8 тепер ловить це на збірці.

## 5.1 Чек-лист стартового набору

Перевірено на поточному стані фікстур. Кожен пункт — конкретний файл
або поле, не загальне "додати контент".

### `altaco-catalog` (CASE · STATIC · MATERIAL · feature)
- **cover** — 1 фото, пропорція 1:1, ≥2400×2400px. Замінити
  `cover.placeholder.jpg`.
- **body** (uk.md, en.md) — наявний текст чернетковий, написаний як
  фікстура. Переглянути й затвердити або переписати за структурою
  задача→підхід→результат (розділ 5 вище).
- `tags` — наявні (`каталог`, `altaco`), можна лишити.
- `endpoint`/`build_ref` — свідомо відсутні (демо ще не існує).
  Додати разом і повернути `status: DEMO`, коли з'явиться реальна
  збірка демо — не раніше.

### `agent-workflow` (PROTOTYPE · STATIC · MONOCHROME)
- **cover** — 1 фото, пропорція 4:3, ≥2400×1800px. Замінити
  `cover.placeholder.jpg`.
- `title`/`summary` — наявні, короткі, у межах ліміту. Можна лишити
  або уточнити.
- `body` — не обов'язковий для цього типу; додати короткий опис за
  бажанням.

### `synthetic-structures-01` (VISUAL_STUDY · STATIC · CHROMATIC)
- **media[]** — заявлено 2 (`m1`, `m2`) з плейсхолдер-alt.
  Типовий обсяг послідовності — 6–8 зображень 16:9, ≥2400×1350px
  кожне, `alt` для кожного двома мовами (замінити плейсхолдер-alt
  у `uk.md`/`en.md`). Розширити до 6–8 або свідомо лишити 2.
- **cover** — 1 фото, 16:9, ≥2400×1350px. Замінити
  `cover.placeholder.jpg`.
- `body` — опційний короткий текст, не критично.

### `organic-intelligence` (VISUAL_STUDY · STATIC · ORGANIC)
- **media[]** — те саме, що й `synthetic-structures-01`: заявлено 2
  (`m1`, `m2`) з плейсхолдер-alt, типовий обсяг 6–8 зображень,
  пропорція 3:4 (портрет), ≥1800×2400px кожне, `alt` двома мовами.
- **cover** — 1 фото, 3:4, ≥1800×2400px. Замінити
  `cover.placeholder.jpg`.
- `body` — опційний, не критично.

### `what-neurica-is` (EDITORIAL · STATIC · MONOCHROME · feature)
- **cover** — 1 фото, 4:3, ≥2400×1800px. Не показується в тілі
  сторінки (правило шаблону EDITORIAL), але потрібна для картки в
  стрічці й og:image — не пропускати. Замінити
  `cover.placeholder.jpg`.
- **body** (uk.md, en.md) — наявний, маніфестного тону. Переглянути
  й затвердити як фінальний текст майданчика.
- `tags` — наявні (`маніфест`/`manifesto`), можна лишити.

**Спільне для всіх п'яти:** жодного реального зображення в
репозиторії немає — усі `cover`/`media` зараз 1×1-піксельні
заглушки. Це єдиний блокер, який стосується кожного об'єкта без
винятку.
