## Запуск

1. **Спосіб злиття.** Рекомендовано merge commit: він збереже історію
   рішень і дасть одну явну межу релізу для відкату. Перед злиттям
   перевірити, що GitHub дозволяє цей спосіб. Не виконувати rebase
   чи force-push. Якщо обрано squash, зафіксувати це для відкату.
2. **Після злиття** записати SHA merge/squash-коміту через GitHub PR/API
   або після `git fetch origin` через `git log -1 origin/main`.
   Порівняти його з commit SHA опублікованого production deploy.
   Локальна гілка main без fetch не є доказом фактичного стану.
3. **Підтвердити успішний production deploy**: у Netlify-панелі
   деплой зі статусом «Published» на потрібному SHA; за відсутності
   доступу до панелі — дочекатись, поки production-URL почне
   показувати нову версію (наприклад, за новим текстом маніфесту
   чи новою формою на `/about/`), і зафіксувати час і спосіб перевірки.

## Відкат

**Ознаки, за яких потрібен відкат:**
- Production-домен показує зламану сторінку (500-ті помилки,
  порожній build) після деплою нового `main`.
- Каталог ALTACO не завантажується, кошик або генерація PDF
  видають помилку в консолі браузера на production.
- Форма контактів не проходить form detection на production
  (не з'являється в списку Forms) і виправити це швидко не вдається.
- Будь-яка регресія, що блокує основний сценарій (перегляд каталогу,
  контакти, мовні переходи) і не виправляється точковим фіксом
  протягом розумного часу.

**Кроки відновлення через Netlify (якщо цей механізм доступний):**
1. У Netlify-панелі проєкту відкрити список Deploys.
2. Знайти deploy за заздалегідь записаним ID/URL і SHA (див. нижче).
   Не вибирати його лише за датою або неперевіреним тегом.
3. Використати опцію «Publish deploy» (або аналогічну) на цьому
   попередньому deploy, щоб повернути його як активний production
   без зміни `main` у git.
4. Після цього обов'язково узгодити Git і Netlify: `main` у GitHub
   лишається на новому SHA (Netlify-відкат не рухає git), тож
   потрібно або (а) окремо повідомити команду, що production і `main`
   тимчасово розійшлися, до виправлення й повторного деплою,
   або (б) зробити запасний шлях нижче, якщо потрібно повернути
   і сам `main`.

**Запасний шлях без Netlify UI (revert-коміт/PR):**
1. Не використовувати `git reset` чи force-push на `main`.
2. В окремій гілці від актуального origin/main підготувати revert:
   - для merge-коміту: `git revert -m 1 <MERGE_SHA>`, попередньо
     перевіривши, що перший батько — main до злиття;
   - для squash-коміту: `git revert <SQUASH_SHA>`.
   Це шаблони майбутньої дії, не команди для запуску зараз.
   Якщо після релізу є інші зміни — оцінити їх і конфлікти окремо.
3. Перевірити diff і повернення потрібних файлів/конфігурації. Виконати
   перевірки старого статичного сайту, визначені його workflow/README,
   та перегляд uk/en. Не вимагати 47 каталожних тестів чи Astro-збірки,
   яких у старій версії немає. Створити окремий revert-PR.
4. Після погодженого злиття revert-PR підтвердити успішний deploy і
   фактичний збіг його SHA з новим origin/main. Автоматичний деплой
   може бути вимкнений або завершитися помилкою — збіг не припускати.

Повернення старої версії також прибере новий каталог і форму пілотів
з основного домену. Це аварійне відновлення попереднього сайту,
а не спосіб зберегти нові можливості під час ремонту.

**Після публікації тега `neurica-pre-relaunch-2026-09-16`:**
- Дозволяє будь-кому знайти точний код старої версії (`git checkout
  neurica-pre-relaunch-2026-09-16`) для порівняння чи ручного відновлення
  файлів коду.
- **Не** відновлює DNS, налаштування Netlify (redirects/headers поза
  git, env-змінні, form notifications), дані вже надісланих форм
  чи будь-який стан, що живе поза цим git-репозиторієм. Відкат
  цих речей — окремі дії в Netlify-панелі й DNS-провайдері,
  цей чек-лист їх не виконує і не гарантує.
